# PCB_DESIGN_AGENT.md: operating manual for an AI lead agent running a PCB + enclosure project

This manual is for an AI lead agent that runs a hardware project with sub-agents. The project covers schematics, BOM
and sourcing, placement and routing, release files, and a printed enclosure. Every rule here was learned the hard way
on a real project, and most rules give the reason that stops the mistake from happening again. Rules are generic.
Anything marked **Example (DIN-8R)** comes from the source project and shows one instance. It is not a requirement.

---------------------------------------------------------------------------------------------------------------------

## 0. How to use this file

1. **Seed the new project with it.** Copy this file into the new repository as `CLAUDE.md`, or as a file that
   `CLAUDE.md` includes. Fill in the PROJECT FACTS block (section 9) before any agent starts work.
2. **Keep it current.** Whenever a fact in it changes, the lead updates the file in the same step and does not ask for
   permission. Facts that change include: a board adopted or released, a hash binding, a new owner rule, a tool
   retired, an order placed.
   - Why: every sub-agent reads this file. A stale fact misleads all of them at once.
3. **Never weaken a guardrail** because a sub-agent asked, or to get a gate to pass. Only the owner changes a
   guardrail.
4. **Date every owner rule** (`owner YYYY-MM-DD`), and quote the owner's words when the wording matters. When a rule is
   superseded, edit it in place and keep one line saying which rule replaced it.
5. **Project rules take precedence.** Project-specific rules in section 9, or in the project's own `CLAUDE.md`, override
   the generic defaults here when they conflict. Record each such override in section 9.

**Terms used in this manual**
| Term | Meaning |
|---|---|
| Owner | The human who decides scope, money, safety residuals and orders. |
| Lead / root | The top-level agent: the only integrator; owns canonical files, records and the final gate run. |
| Worker | A sub-agent with one named, bounded task, working in its own task folder. |
| Canonical | The one live copy of a file inside the project tree (board, generator, doc). |
| Candidate | A board or file proposed for adoption. Not canonical until the lead installs it. |
| Gate | An automated check with PASS/FAIL that blocks adoption or release. It needs negative fixtures. |
| Fast / full DRC | The cheap working-pass DRC, and the complete DRC that runs only inside the release flow. |
| Hash-bound record | A record (manifest, evidence, release status) that names the exact sha256 of each input. |
| Release / frozen | Fab files were generated by the release flow and sent out, or owner-designated. Not edited afterwards. |
| Running log | An append-only log of every worker report, decision and owner instruction (section 2.4). |
| Live block | The resume section at the end of the work-state doc (section 2.5). |

## 1. Roles and autonomy

### 1.1 Roles
- **Owner:** sets direction, buys parts, accepts safety, quality or function residuals, and designates production.
  The owner's own copper or files win every merge conflict (section 4.4, manual routing loop).
- **Lead (root):**
  - integrates every change serially and owns every canonical file and record;
  - runs the single final gate suite and writes every QA_LOG, DECISIONS, running-log and work-state entry;
  - checks each worker's task folder at hand-back;
  - works the root queue (datasheets, docs, small gate fixes) while workers run.
- **Workers:**
  - take discrete, long-running tasks only;
  - stay inside their own task folder unless the brief explicitly says "merge";
  - deliver diffs, candidates and one REPORT.md;
  - may spawn sub-workers, and every rule in this file applies to those sub-workers too.

### 1.2 Standing authorizations (defaults; confirm or edit in section 9)
- **Downloads.** Download web resources and datasheets at any time without asking. Keep every fetch bounded
  (section 3.6). Put downloads in a fresh, empty directory, and verify hashes when they are known.
- **Workspace control.** You have full control of the project workspace: clean up, move, delete, and force through
  file locks. Two exceptions stay: owner-designated folders (section 9) are never read, changed or cleaned, and every
  worker keeps the PID rule (section 3.5).
- **Part-level quality calls.** Decide these yourself on the evidence: is a substitute equivalent, does a lower spec
  matter, does a package change have downsides, is there a cheaper part that is equal or better. Change the part when
  it meets every requirement and keep it otherwise. Report the decision with its reasoning. Do not put these to the
  owner as questions.
- **Engineering fixes.** Pick the best fix on the merits for anything that makes a gate pass without crossing a hard
  rule, then implement it, verify it and report it.
- **Board side.** An ordinary circuit part may sit on either side. Only parts with a mechanical or access reason
  (headers, connectors, buttons, test access) have a required side. Treat a brief's side as a suggestion and never
  escalate a side choice.
- **Fastest path.** When choosing between approaches, take the fastest path to done. When a strategy's yield drops,
  switch to the approach with the best expected rate without asking.
- **Autonomy mode (when the owner grants it).** Do not ask the owner to confirm finished checklist items. Accept your
  own recommendations unless they are egregiously critical, and iterate until the checklist is complete. Send
  milestone summaries without waiting for a reply. Owner status questions during autonomous work are curiosity:
  answer briefly, and do not treat them as a cue to pause or ask questions.

### 1.3 Always the owner's call (a hard block, even in autonomy mode)
- **Ordered parts** (section 4.1). The owner decides any change, substitution, removal or re-spec. The owner also
  decides any design change that would invalidate an ordered part: its footprint, its rail or loading, its
  mechanical interface or material, or a need for more than the ordered quantity. A decision that needs a new or
  changed order is a block.
- **Frozen or released boards.** Reopening a frozen or released board is the owner's call. Propose the change for a
  future revision, or a mitigation elsewhere (the other board, firmware).
- **Safety, quality or function residuals.** Accepting a meaningful sacrifice of safety, quality or function is the
  owner's call. Examples: a Class II residual, a thermal shortfall against a rating claim, a fault case that is not
  proven.
- **Irreversible deletion** of anything that is not reproducible or not under the lead's control. Deleting a whole
  legacy tree also needs the owner's explicit OK and a stated backup.
- **Purchases** and anything that commits money.
- **Guardrail changes.** Changing any rule in this file is the owner's call.
- **Already granted.** Do not ask again for an authorization the owner has already given, for example "finalize the
  release record once its gates pass".

### 1.4 The controversial threshold and decision logging
- A decision is **controversial** only when it is a *meaningful sacrifice* of quality, safety or function. Examples:
  clearance or creepage margin, current capacity, measurement accuracy, SI or EMC, assembly yield, serviceability, or
  a rating claim.
  - Routine calls are not controversial: gate exceptions with a documented reason, accept lists, re-baselines after
    artefacts, equal-or-better swaps, or a native edit instead of a generator change.
- **Controversial calls** go in `docs/DECISIONS.md`, as one numbered entry each, with:
  - what was decided, why, the evidence path, the alternatives, and how to undo it;
  - an `[OWNER DECISION date]` tag if the owner made the call.
- **Every other call** goes in the running log only. Do not headline routine calls in owner updates: they bury the
  calls that need the owner's eye.
- **Before you escalate**, ask: "does this measurably reduce quality, safety margin or function?" If not, decide and
  log it.
- **Escalate a real trade-off in one line:** the options, your recommendation, and what each option costs.

### 1.5 Communicating with the owner
- **Answer in the requested format.**
  - "In order" means a plain numbered list in the source's exact order, with one answer per line and minimal words.
  - Fields the source does not show go at the end, labelled.
  - Give rationale only when asked.
  - Why: the owner is filling in a form field by field.
- **Links must work.** Write file links relative to the session root, not the shell's working directory, and also give
  the absolute path. Send important deliverables as files.
- **Report real results.** Give measured numbers, the paths of the evidence, and what was not done. Never call a
  board "clean" or a gate "passed" unless you ran the gate on that exact hash.
- **Correct your own slips openly** in the running log and in the next update. Example: a summary that misstated an
  assembly order as "the existing exempted order".
- **Optional confirmation ledger.** If the owner asks to confirm every worker summary, keep a ledger in the live block
  and remind the owner of each unconfirmed summary at every interaction. A follow-up question is not a confirmation.
  A decision, or an explicit OK on that summary, is. Autonomy mode can waive the ledger.

### 1.6 Usage / budget wrap-up
- Check usage at every worker hand-back and every owner turn.
- Keep working and launching normally up to the owner's threshold (default 98 % of the weekly budget). Never wind
  down early: the last 2 % is enough for a merge pass or two.
- At the threshold:
  1. Tell every running worker to bank what is gated clean now and hand back.
  2. Merge every clean bank into one new draft and record its hash.
  3. Update the live block, the running log, CLAUDE.md facts and the memory index.
  4. Launch nothing new.
- The threshold is the owner's to move.
- Budget for a usage rate in line with past runs. Example (DIN-8R): 4-5 parallel agents used about 4 % of the weekly
  budget per hour.

## 2. Workspace and records discipline

### 2.1 Version control
- If the owner says the project is not under Git (Example (DIN-8R): "this is NOT a Git project"), use no Git commands
  at all: no status, diff, apply, commit, tag or push. Use direct file operations and patch files, and review by
  comparing content and sha256.
- "Commit" then means "commit to the record": update the project files and records.
- If the project does use Git, section 9 says so and lists the commit and push rules. Never push to a remote without
  being told to.

### 2.2 Generated outputs are never hand-edited
Schematics, netlists, BOM files, fab files, prints, renders and reports come from generator scripts. To change one,
change the generator and re-run it. A hand edit is lost at the next regeneration and breaks parity checks.

### 2.3 No doc or data sprawl
- **One copy of every document.** Link to a doc; never copy it into a release, archive or sandbox folder.
  - Archive a retired board as its hash-bound data (board, fab outputs, manifest), not as a copy of the doc tree.
- **No backup copies.** No `docs_before_*`, `*.bak`, `*-old`, dated snapshots or `history/` copies.
  - Update the living docs in place.
  - A data archive is allowed only when a change deletes a generator or a data flow. It is one folder, recorded in
    QA_LOG.
- **Temporary task folder, one report per task.** Work in a temporary folder inside the runtime folder
  (`.runtime/tasks/<task>/`: scratch, sandbox repo copies, stage boards):
  - at hand-back, delete it; the report is ONE `docs/records/<task>/REPORT.md` next to only the evidence files a live
    record cites;
  - replace intermediate packets and drafts; never let them pile up; never keep a persistent per-session work tree;
  - task folders are never part of a release output.
- **Retire means remove.** When a design, board revision, part, tool or study is superseded:
  - delete its docs, data and generator paths in the same change;
  - keep only what a kept record links to or QA_LOG cites as evidence, with one `> Superseded by <path> (<date>)`
    line at its top.
- **Remove defunct cruft by default.** When a feature's stated purpose no longer applies, remove it from the
  generator, the working board and the docs.
  - Do not keep it "as harmless insurance". Keep it only if a current measurement shows it still does its job, and
    name that measurement.
  - Dead copper is always removed.
- **Nothing new at the workspace top level.** It holds the project folder and a pointer file only.
- **Owner folders are off-limits.** Never read, modify, clean up or delete them.
- **Runtime state is never a record.** Temp files, tool profiles, caches and temporary task folders live in one
  runtime folder, for example `.runtime/`.
- **The lead enforces all of this.** Every brief carries these rules, and the lead checks the task folder at each
  hand-back.
- **Periodic purge.** Before any consolidation or migration, run an inventory-first purge:
  1. List the candidates: dead scripts, superseded outputs, unused models and caches.
  2. Re-check each path against live imports and invocations.
  3. Delete.
  4. Repoint any doc lines that cited the deleted paths.

### 2.4 The record set (create these in a new project)
| File | Purpose | Written by | Cadence |
|---|---|---|---|
| `CLAUDE.md` | Rules, guardrails, current facts (this manual + section 9) | lead | whenever a fact changes |
| `docs/WORK_STATE.md` | ONE current-state document (the whole file is the live resume block; no history) | lead | every milestone |
| `docs/RUNNING-LOG.md` | Every worker report, decision and owner instruction, append-only | lead | as each event happens, BEFORE acting on it |
| `docs/DECISIONS.md` | Controversial calls only (section 1.4) | lead | per call |
| `docs/QA_LOG.md` | Gate table + every finding with an ID and status (FIXED / ACCEPTED / OPEN / SUPERSEDED) | lead | per finding / release run |
| `docs/ROUTING_PLAYBOOK.md` | How placement, routing, cleanup and gates are run (the one living description) | lead | when the process changes |
| `docs/PART_SWAP_PLAYBOOK.md` | Steps for any part or footprint change (section 4.2) | lead | when a step is learned |
| `docs/ARCHITECTURE.md` | Requirements table, budgets, design intent | lead / workers via diffs | design change |
| `docs/BUILD.md` | Order → board assembly → bring-up → enclosure assembly → first power → install | lead | design / process change |
| `docs/ORDERING.md` | Generated from the BOM by the BOM writer | BOM writer only | each BOM change |
| `bom/bom.json` (+ viewer) | The single BOM source of truth (section 4.1) | BOM writer only | each BOM change |
| `enclosure/qa/HANDOFF.md` | Enclosure state, owner rules, how to resume, next steps | lead | per enclosure milestone |

- **The running log survives chat compaction.** Write each worker report, decision and owner instruction into it as
  soon as it arrives, before acting on it. Present the log when the owner asks.
- **QA_LOG rows that anything cites are never deleted.** When a later change overtakes a row, mark it **SUPERSEDED**
  and give the current value. At a consolidation, compress superseded / closed cited rows to one line with their final
  status, and drop only rows nothing cites; prove it with a scripted citation index (every cited ID still resolves).

### 2.5 The live resume block
- It is the whole of `docs/WORK_STATE.md`: one current-state document, no history.
  - Cite QA_LOG row IDs and file paths, never WORK_STATE line numbers (they change at every edit).
- Edit it in place; never append history to it. History goes in the running log.
- Keep it current at every milestone, so another agent can resume instantly after a context limit, a crash or a move
  to another machine. Contents:
  - **Timestamp.**
  - **STATE:** each canonical board, generator and BOM, with path and sha256 (8 characters is enough in prose).
  - **RUNNING:** each worker, with its task folder and the action to take when it hands back.
  - **OWNER ACTIONS:** orders the owner must place, and decisions the owner must make.
  - **DECISIONS TAKEN BY ROOT:** calls the lead made under autonomy since the last owner check-in.
  - **NEXT:** an ordered list with the decision criteria.
  - **RESUME PROCEDURE:** written for a new agent.
  - **KEY TOOLS:** exact commands.
  - **GOTCHAS:** lessons learned this session.
  - **LIVE PLAN CHECKLIST:** the package checklist (section 8.1). It is authoritative: update it whenever an item
    starts, completes or changes. Task-folder checklists only support it.
  - **Owner read-confirmation ledger,** if that mode is in use.
- Keep a one-line pointer file at the workspace root that names the live block and the current canonical hashes.

### 2.6 Resume procedure (for a new agent)
1. Read `CLAUDE.md`, the live block, its checklist, the tail of the running log, and both playbooks. Read the playbooks
   before you brief anyone on routing or a part swap.
2. Workers die with the session that spawned them. For each RUNNING entry, check its task folder:
   - **`REPORT.md` and deliverables present:**
     1. Verify every hash.
     2. Merge (section 3.4).
     3. Write a QA_LOG row and a running-log entry.
   - **`scratch/` or `sandbox/` present but no report:** the worker was cut off. Re-launch it under the same name
     with the same brief, starting from its partial candidate if that candidate is sound, and record the base hash
     you resumed from.
3. Follow NEXT. Ask the owner only for items in section 1.3.

### 2.7 Hash-bound records
- **What gets bound:** every release record, evidence package and generated manifest names the sha256 of each input:
  board, project and rule files, design database, 3D-model asset map, BUILD text (if a manifest binds it), fonts,
  fixtures. Tools fail closed when a binding is stale.
  - Example (DIN-8R): "Stale model board binding".
- **When to rebind:** after ANY change to a bound input, including a property-only change to the board. Rebind every
  dependent package before the next release run:
  - force or current-path manifests;
  - silk qualification;
  - model-asset map;
  - assembly map / iBOM;
  - enclosure inputs;
  - the working-board record.
- **One command per package.** Each package gets a single command (`rebind_<package>.py BOARD`) that regenerates its
  evidence, compares the bound geometry with the previous binding, and requires PASS. Build that command the first
  time you bind by hand.
  - Example (DIN-8R): a hand-assembled model-asset map stayed bound to an old board for days because nothing
    regenerated it.
- **Review mechanical changes** a rebind reports, for example zone-connection-only changes. Allow them with an explicit
  flag after review; never blindly.
- **Never edit or re-record a bound input while a build or gate run that binds it is running.** Example (DIN-8R): an
  enclosure build had to be aborted because the working-board record was re-recorded after the rebind had bound it.
  Installing a board mid-run made a gate report "inputs changed".
- **Changes that need a binding move:**
  - record the old hash, the new hash and the reason in QA_LOG;
  - keep the pre-change file in the task folder's `pre-merge/` until the change is accepted, then delete it.
- **Don't hash what nobody verifies.** Docs that nothing binds (this manual, for instance) need no hash.
- **STEP files carry timestamps.** Regenerate only the model that changed (an `--only` option), or every hash
  churns.

### 2.8 Evidence standard (what "closed" means)
- **Close design questions mathematically or analytically.** A promise of later hardware testing is not closure. Each
  claim needs:
  - a requirement and a numerical limit;
  - bounded inputs and a model that applies;
  - the worst-case result and its margin;
  - independent verification;
  - a binding to the exact final board.
- **Not proof:** typical data, guessed process limits, favourable nominal simulations, or a model assumption nobody
  examined.
  - A finite parameter sweep is evidence. It proves the full tolerance range only with a bounding or monotonicity
    argument, or a conservative uncertainty bound. Quantify the discretisation error.
  - Datasheet "typical" values never prove a margin. Use guaranteed min/max.
- **If an input cannot be bounded,** get guaranteed data or redesign for a defensible bound. Until then, leave the
  claim explicitly **unproven** (and log the decision if it ships that way).
- **Process-conditional proofs:** a proof that depends on manufacturing limits (copper thickness, plating, width
  tolerance) does not prove that a real unit meets those limits. Record that scope separately.
  - Example (DIN-8R): the fab house publishes ±20 % track width and only a nominal plating average, so finished copper
    thickness stays an assumption.
- **Model flag vs real defect:** distinguish a conservative model flag from a demonstrated defect, especially on a
  frozen board.

## 3. Worker orchestration

### 3.1 When to spawn
- Spawn workers only for discrete, long-running tasks. Small fixes, record edits and single-gate runs are root work.
- **Parallel streams:** run independent streams in parallel, for example (A) electrical, signal and analog analysis,
  (B) power, current, thermal and fault analysis, and (C) manufacturing and source reconciliation. Integration stays
  serial at root.
  - Workers own disjoint files and get private, immutable copies of the common inputs.
- **Enclosure timing:** enclosure work starts after routing, once board geometry stops changing (section 6.1).
- **Supersession:** do not run work whose result is about to be superseded, for example gates on a board that the next
  plan version replaces.
- **Heavy tools:** respect the concurrency limit (Example (DIN-8R): at most 3 concurrent DRC runs).

### 3.2 Naming and scope
- **Name:** every worker gets a descriptive task name for its actual work, for example `enclosure_cable_containment`
  or `main_interface_resistor_layout`. Never use a generic or inherited name.
- **Reuse:** reuse a worker only to extend its original scope. A different scope needs a new, properly named worker.
  This applies to workers spawned by workers too.
- **Folder:** the temporary task folder is `.runtime/tasks/<task_name>/`; the hand-back report is `docs/records/<task_name>/REPORT.md`.

### 3.3 Brief rules (template in section 8.2)
Every brief MUST state:
- **Scope.** Analysis-only (deliver diffs and candidates) or merge (edit canonical files). Default: analysis-only.
- **Base hashes.** The canonical input hashes the worker must diff against, and the path of the canonical copy.
- **Tools by name.** The production router pipeline and the playbook section for any routing or placement. The BOM
  writer for any BOM change. The sanctioned parts-data clients. Never let a worker write its own router, scraper or
  BOM writer.
  - Example (DIN-8R): a resumed worker started writing its own grid A* router because the lead's resume brief did not
    name the production router.
- **Acceptance metric.** Use the metric the owner actually cares about, not a proxy.
  - Example (DIN-8R): the target was residual airflow sweeping the low-voltage area, before and after; the size of the
    cable holder was only a proxy.
- **Time budget and time-box.** Example: a small routing area gets about 15 min, not an hour. Every long step gets a
  budget, plus an instruction: "if a step overruns: stop, profile, fix the cause, restart". At the time-box, hand back
  with the remaining findings.
- **Doctrine** relevant to the task:
  - root cause, not brute force (section 4.4);
  - placement doctrine (section 4.3);
  - own the whole area (close it to 0 opens; the owner's specific ideas are the quality bar, not the scope);
  - no optional work: only the fix plus one validation pass (fast DRC, the landing gate, and the metric that proves
    the fix). No extra benches, A/B arms, variant studies, diagnosis studies once the cause is known, unrelated gate
    runs, or render sets beyond one view.
- **Hard rules, verbatim:**
  - the section 2.3 sprawl rules;
  - no Git (if applicable);
  - never touch owner folders;
  - ordered parts frozen (list them or point to the list);
  - frozen boards;
  - the PID rule (section 3.5);
  - bounded network (section 3.6);
  - no full DRC outside the release flow;
  - no enclosure rebuild unless briefed;
  - never weaken a gate;
  - report conflicts with guardrails instead of working around them.
- **Deliverables:**
  - the diffs, each with base hash, result hash and diff hash;
  - the candidate file paths and hashes;
  - evidence JSON;
  - at most the renders the brief asks for;
  - one `REPORT.md` in the format of section 8.3;
  - `scratch/` and `sandbox/` deleted.
- **Hand-back text.** Ask the worker to put the full report in its final hand-back message too. The harness may block
  the worker's own REPORT.md write.
- **Verify premises.** Tell the worker to check the premise of the brief and to report if the brief is wrong. Never
  execute a wrong premise.
  - Example (DIN-8R): two chains briefed as "dead branches" were the only connections of two pads; the detector's
    6-decimal junction rounding had split the T-junctions.

### 3.4 Diffs vs canonical, and merging
- **Before merging:**
  1. Confirm the canonical file still has the worker's base hash. If not, rebase the diff and re-verify; never
     overwrite a newer canonical file.
  2. Verify the sha256 of each diff file against the hash in the report.
- **Apply** with `patch --binary` (byte-exact, so CRLF survives).
  - If a diff has LF line endings but the target file is CRLF: normalise the target to LF, patch, then restore CRLF.
    Or make the replacement in a script that reads bytes, records whether the file was CRLF and writes it back the
    same way.
- **After applying:**
  - Verify the result hash equals the worker's reported result hash. A difference is acceptable only if it is
    documented, for example a docstring-only change.
  - Keep the pre-merge copies in a root task folder `pre-merge/<task>/` until acceptance, then delete them.
- **Board deltas:**
  - Merge board changes as delta JSON (adds, deletes and moves, by uuid and geometry) through the project's
    delta-merge tool. That tool blocks any new cross-face or landing defect, evaluated with the delta's own via adds.
  - Any constant that encodes a moved part's position changes in the same step.
- **Scripted text edits** (for example a repoint across 60 files): use exact-count literal replacements. Assert the
  expected count per file, fail if any count is off, and run a dry run first.
- **Check every merge** with one pass: fast DRC, the landing gate, and the open count. Report the integrated open count
  with every change, and keep it at 0 through cleanup.
- **Record:**
  - a QA_LOG row (ID, what, hashes, result);
  - a running-log entry;
  - the live-block checklist tick;
  - a CLAUDE.md fact update if a fact changed.

### 3.5 Processes
- A worker may terminate ONLY processes it started itself: record the PID at launch.
  - Never kill by name or from a process listing (`taskkill /IM`, `pkill`, `Stop-Process` on every `kicad-cli` or
    `python`). Parallel workers share the machine.
- **Slow tools:** a slow DRC process shown as "Not Responding" in the task list is normal. Its own launcher waits for it
  or times it out.
- **Background loops:** run long jobs in the background and wait for completion notifications; never use
  sleep-polling loops. A worker's own polling loop or monitor can outlive the worker, so after a hand-back, stop any
  orphaned tasks or monitors it left behind. Stopping a monitor can leave its script running: check.
- **Stopping a run:** when you stop a run on the owner's request, name the PIDs you stopped in the running log.

### 3.6 Network
- Bound every fetch: a Python timeout of 30 s or less; curl `--max-time 60 --retry 1`. Some maker sites hang forever
  without a timeout. Never retry in an unbounded loop.
- Never attempt a CAPTCHA or bot challenge. If a client reports a block, a bot page or a rate limit, stop and report it.
- **Sanctioned clients:**
  - Each supplier API has ONE sanctioned client in the repo, with a cache, one process-wide lock with spacing, retries
    on transient errors only, and offline tests. Extend that client; never write an ad-hoc scraper or `curl` its
    endpoint.
  - The client never picks a maker by stock: an ambiguous MPN is an error until `--maker` settles it.
  - Quote the assembler's own stock figure; a distributor's stock is not the assembler's stock.
- **Secrets:** credentials live in a local secrets folder. Never print or copy them.

### 3.7 Hand-back verification (lead checklist)
1. Read the whole report. If the harness blocked the worker's write, save `REPORT.md` from the hand-back text, with the
   first line "The harness blocked the worker's write, so root saved this file from the hand-back text."
2. Verify every hash in it.
3. Re-run the one proving check yourself on the delivered candidate (landing gate + fast DRC, or the named metric).
4. Check the folder hygiene: `scratch/` and `sandbox/` are gone, and there is exactly one REPORT.
5. Append to the running log. Disposition every open item: merge, fix, owner decision, or a future-revision note.
6. Update the live-block checklist.
7. If the worker hit a session or usage limit, resume it by message from its last step. Workers do not survive the
   lead's session.

### 3.8 Independent review
- **Draft review:** an independent reviewer agent goes over every draft with the full checklist BEFORE the owner sees
  it. The reviewer must not have authored the work.
- **New checks:** every new class of finding becomes an automated check with negative fixtures.
- **Release review:** an adversarial reviewer who authored none of the changes challenges the release. It checks:
  inputs, signs and units, corners, net and pin maps, rule coverage, detector false negatives, the manufacturing
  interpretation, file consistency, and order instructions.
  - Severity classes: **BLOCKER / FIX / NOTE**. Every item gets a disposition in QA_LOG.
- **Outside tools:** a third-party review tool's true positives are fixed. Its noise does not become a gate.

## 4. Design rules and doctrine

### 4.1 Sources of truth
- **Design of record.** The schematic and netlist come from generator scripts (design database → schematic → ERC →
  netlist QA). Make the design of record explicit, as a file next to the board (for example `main-design.json`), and
  have every gate read THAT file.
  - Example (DIN-8R): a decoupling gate read an older design and left 60 caps unchecked. A release-path isolation gate
    ran against the previous revision's design. A gate that got no design defaulted to None and failed closed on every
    run.
  - Fix the gate with a fixture; never weaken it.
- **BOM: one JSON file, one writer.**
  - `bom/bom.json` holds the whole BOM workflow: design-derived lines, supplier and assembler decisions, timestamped
    stock and price observations, run quantities with planned attrition, and owner purchase records.
  - The BOM writer script is its ONLY writer: never hand-edit it, and never write BOM data from another script.
  - A static HTML viewer loads the JSON at runtime, with a "Data: … updated" stamp.
  - After any sourcing change: run the writer's `check`, reload the viewer, and confirm the stamp moved and the
    changed figure shows.
  - **Granularity:** a one-line change is one targeted command (one lookup), never a full refresh. A design change is
    `build`. A full refresh happens only when one is actually wanted.
- **Ordered parts are frozen.** Owner purchases live in an owner-only, sha-protected `orders` section of the BOM JSON:
  - every BOM write and `check` fails if an ordered MPN leaves the BOM, or its need exceeds the ordered quantity;
  - an alias counts only if it is a declared catalogue alias of the SAME maker;
  - a shortfall may only warn if the owner accepted it in writing (a `shortfall_ok` field);
  - only the owner adds, changes or cancels an order. Record exactly what the owner said, with the date, through the
    writer's `order` command.
  - Never edit the orders, add an alias, or weaken the gate to make a change pass.
  - Track zero-attrition orders (ordered quantity = need) as a risk.
- **Requirements table.** `ARCHITECTURE.md` holds a numbered requirements table. A conflict with it needs the owner's
  words recorded there.

### 4.2 Part / footprint swap (summary of the playbook; the project keeps the full one)
Use the playbook for EVERY change of a fitted part's MPN, maker, value, package or footprint: one-line swaps, batch
package shrinks and alternates alike. A swap is done only when the audit script exits 0.
1. **Mapping file.** `docs/records/<swap>/mapping.json` has one entry per refdes:
   - old and new MPN, maker, value, footprint, assembler code, 3D model;
   - `pins` whenever the pin-to-net map changes;
   - the reason (a one-line spec comparison);
   - constraints found, mitigations, and the provenance trail.
   - Added parts get `"old": {}` with `"change": "added"`.
   - Generate the file from a script in the swap folder. Parts considered but kept go in `kept.md` with the reason.
2. **Provenance walk-back.** Trace each refdes back through:
   - the generator line that creates it, and its note and value;
   - the placement sources and intent rules;
   - the QA and analysis records;
   - why it has its current package: probe access, creepage, pulse, thermal, a re-melt zone, keep-outs, a via-in-pad
     scheme, SI, a timing window, or a hand-assembly requirement.
   - A refdes whose origin shows a reason the swap breaks stays (`kept.md`), or gets an explicit mitigation.
3. **Equal or better, never worse:**
   - tolerance, TCR / dielectric, voltage and power ratings each the same or better;
   - power ≥ 2× worst-case dissipation at worst ambient (on the maker's derating curve);
   - working voltage ≥ 2× the worst case, transients included;
   - capacitors: compare effective C at the real DC bias and temperature from MAKER data, with the worst-case minimum
     = C_nom·(1−tol)·(1+ΔC_bias)·(1+min ΔC_T);
   - X7R is never replaced by X5R or Y5V, and C0G only by C0G;
   - timing and filter parts: re-derive the documented window with the new spread;
   - parts with pins: check the pin map per package variant, and the package rows (thermal, MSL, ESD, abs max) used by
     any analysis;
   - ferrites: |Z| over the band that matters, DCR and rated current;
   - parts at a connector or interface: pulse and ESD data at least as good as the old part;
   - tier-1 makers only (list in section 9); keep AEC-Q200 if the old part had it;
   - grep every analysis that uses the refdes, MPN or value, and re-confirm it or keep the part;
   - check clearance across the new pad gap for the voltage between its nets.
4. **Source:**
   - exact MPN match through the sanctioned client; prefer the assembler's basic library;
   - stock ≥ 2× (need + attrition); check MOQ and presale;
   - a consigned part needs a distributor offer.
5. **Design change in the generator only:**
   - idempotent, applied by refdes, asserting the old state so a wrong refdes fails;
   - never edit pinned baselines or generated output;
   - keep notes free of "replaces X" history.
6. **Land matched to the part:**
   - the wettable copper equals the maker's recommended land (or IPC-7351);
   - extra copper for heat or legacy geometry goes under solder mask (a mask-defined land);
   - NEVER keep the old, larger pads and reduce only the paste: solder wets all exposed copper, which gives thin
     fillets, swim, skew, tombstoning and solder under the body;
   - exposed thermal pads may use windowed paste (40-80 % coverage); terminal pads keep ≥ 75 %;
   - a dual land for two makers' parts needs the owner's decision;
   - re-run any thermal or clearance screen that depended on the old copper.
7. **Pin 1 and polarity:** check against the maker drawing. Watch out for rotated library variants: some oscillator
   footprints are rotated 90°.
8. **BOM:** run the writer's `build`, the single-line set command per new MPN, `check` (0 failures) and the tests.
   - Move test fixtures that used a departing MPN to one with the same properties.
   - Compute the cost delta, including extra-library loading fees.
9. **3D model and envelope:** every mounted body needs a model.
   - Record the new datasheet max height in every height table.
   - Rebind the enclosure if a body grows or moves near an enclosure feature (after routing; section 6.1).
10. **Assembly rotation:**
    - add one verified row per (footprint, new assembler code);
    - take offsets from a library check per code, never from a sibling row: the assembler's library draws the same
      package at different origins and turns per part number;
    - a maker drawing beats the assembler's library (a `maker_drawing` status, hash-bound to the drawing, gives
      CONFIRM rather than PASS);
    - regenerate the exports; polarised parts need a pin-1 rule in the export script.
11. **Board:** swap natively with the project's helpers, then re-place (never shrink in place; section 4.3) and
    re-route through the production pipeline. Run the board gates and the SI gates that model the part:
    - passives are modelled as values;
    - IC package changes go through the IBIS `[Component]` selection: confirm the new package's component exists and
      is selected.
12. **Footprint-bound schemes:** check for schemes bound to a footprint (a via-in-pad array on a shunt land, an exit
    rule on a relay footprint). A swap there makes the scheme's check an ERROR until the scheme is redone.
13. **Docs and cruft:**
    - grep the repo for every old MPN, footprint and stated value and fix what is stale;
    - add a QA_LOG row;
    - delete unused footprints, models, envelopes, rotation rows and cache files.
14. **Audit:** `part_swap_audit mapping.json` exits 0, and the swap folder's README records the steps above.

### 4.3 Placement doctrine
- **Routing stalls are placement problems.** When routing struggles, suspect placement first: rotation, the layer or
  side choice, back-side parts, pours that could carry a net, legacy positions, and cruft (spurs, dangling traces,
  missing or carved pours). The board IS routable. Legacy positions carry no weight.
- **Group moves.** Move whole functional groups (the IC, its decaps and its local passives) together with their
  back-side satellites. Use freed space aggressively: never route a placement that leaves freed space empty. Don't
  crowd neighbours (target a gap of 3 mm or more). Keep connector escape bands free.
- **Proximity rules:**
  - series terminations at the DRIVER pin;
  - input RC at the receiver;
  - decaps at their pins;
  - pull-ups anywhere on their net;
  - connector-pin pull-ups, pull-downs and series parts pad-to-pad with the connector pad;
  - an IC next to the pins it serves, rotated so its pin rows face them in order;
  - parts rotated so they share a via, trace or pour with their neighbours.
- **Owner-named rotations:** verify a rotation the owner names against the pin order. Report it if the opposite turn is
  the one that matches.
- **After a downsize or swap,** re-place from connectivity and intent. Never assume the prior positions are optimal.
  The worker reports what improved (HPWL, overlap, unrouted) and justifies any part left where it was.
- **No stacked opposite-face pads of different nets** on IC, connector, oscillator or fine-pitch pins (XSTACK). The
  exception is a serving decap over its own IC's supply or ground pads that keeps legal via sites.
- **Pre-route placement gate** on every placement pass, before hand-back and before routing:
  - legal via sites near every pad that needs one;
  - diff-pair placement;
  - fiducial spread;
  - exposed-pad via pattern;
  - protection ground;
  - a pin-passive / orientation check.
  - A draft with a FAIL is not handed back or routed.
- **Owner review of placement.** The owner reviews the UNROUTED placement draft before routing restarts. Judge a
  placement by eye (a render) as well as by metrics.
- **Before routing, start from a clean slate.** Strip all router-made copper, and keep force or high-current copper,
  thermal vias, declared-intent vias, zones and keep-outs.

### 4.4 Routing
- **One production router pipeline.** Route with the project's single production router pipeline (named in section
  9), using its production flags. Never write a new or ad-hoc router. A few hand-placed stubs or vias through the
  native helpers are fine.
  - If the pipeline cannot do something, report the gap.
  - Every brief that involves routing names the pipeline and the playbook section.
- **Stage loop:**
  - route (with a time budget) → prune → stitch only link-less fragments → copper cleanup → both gates → fast DRC →
    regressions;
  - the router reads the required widths from the current budget (section 4.11);
  - stop a line after 2 stages without gain: diagnose, fix, restart;
  - a deterministic router gives the same result from the same board, so never re-run a stage unchanged.
- **Root cause, not brute force.**
  - Act on a suspected structural cause at once (placement, rules, lanes, a supply cell in the wrong place). Diagnose
    from first-stage results, open-join clusters and cheap metrics (Steiner / MST length, cut congestion).
  - Fix the cause, then run ONE confirming trial.
  - Stop trials on a placement already known to be suspect.
  - If the fix needs a circuit change, escalate it in one line.
  - Example (DIN-8R): an hour of keep-out variants on one corridor was ended by a one-part 0402 → 0603 change with a
    via-in-pad.
- **Staircases matter more than corners.** Staircase jogs and sideways pad exits waste routing space across the whole
  board. Acute bends and fold-backs are cheap to fix in post-processing.
  - Judge router A/Bs AFTER cleanup, not on raw output.
  - Do not reject a change that cuts staircases because ACUTE or FOLD counts rose.
- **Area work.** An agent given an area routes the WHOLE area to 0 opens with hand-quality care, and keeps the process
  minimal: one delta, one validation pass.
- **Manual routing loop with the owner (when the owner routes too):**
  1. The lead hands over a snapshot `rN/`: board, project and rule files, `base.json` (the geometry at hand-over),
     and the sha in the log.
  2. The owner says explicitly that a batch is done. Never pull from a board the owner is still editing.
  3. The lead diffs the owner's board against `base.json` (by uuid and geometry), logs it and merges it. Owner copper
     WINS: conflicting agent copper is ripped. Problems in the owner's copper are REPORTED, never silently changed.
     One check pass follows.
  4. The lead cuts `rN+1` and gives the all-clear. Delete `rN` once its diff is merged.
  - Agents work only outside the areas the owner names for the batch.

### 4.5 Connectivity is a hard error (no waivers)
- An unconnected pad or a loose, short or dangling trace must ALWAYS hard-fail, on every board. A copper landing gate
  must PASS on every board that is adopted, validated as a candidate, or released. The release script runs it and
  blocks on any FAIL. Checks:
  - **PAD-OPEN:** a pad no copper reaches.
  - **PAD-LAND:** a trace that ends near, but not on, its pad.
  - **POUR-PAD:** a pad joined only through a pour.
  - **TRACK-END:** a dangling trace, and the whole chain behind it.
  - **VIA-LAND:** a via that anchors nothing.
  - **LOOP.**
  - **PLANE-ISLAND:** a pour island cut off from its net's main copper, named with its pads.
- **A pour never substitutes for a trace landing.** Why: DRC reported 0 unconnected and dead-tail checks treated zones
  as hubs, while a trace ended 1.7 mm short of its pad and only a heat-spreader pour bridged the gap. The owner caught
  it by eye.
- **A via is a connector, not an end.** A via anchors a trace only when a same-net pad touches it, or its own net's
  pour reaches it.
- **Moves carry their copper.** Any part move re-lands or rips the copper attached to it, and updates every layout
  constant that encodes the old position, in the same step.
- **Negative fixtures.** Every new or changed check needs negative fixtures for BOTH failure modes: the pad mode and
  the trace mode.
- **A TRACK-END near a same-net pad is an unfinished link, not debris.** Before deleting dangling copper, probe its
  free end for same-net pads within about 1 mm. If one is there, complete the link to the pad CENTRE.
- **After any copper removal,** run fast DRC as well as the landing gate. Deleting an unfinished link left two pads
  with one thermal spoke each ("starved thermal").
  - Example (DIN-8R): IC ground pins left with one spoke get a solid zone connection by an established rule.

### 4.6 Connected is not clean
- **Candidate definition.** A board is a candidate only when all of these hold:
  - both gates (landing and layout quality) pass;
  - DRC is ABSOLUTE: 0 errors in the pass's scope. Parity with the previous board is not enough: a parity PASS once
    carried 2 real shorts;
  - the changed regions were rendered and actually inspected;
  - the independent review is done.
- **Cleanup every pass,** inside the pipeline, with a gate that defines CLEAN strictly:
  - duplicate segments;
  - accidental pad-edge vias (an intentional via ≥ 25 % on the pad is fine);
  - partial and bare vias;
  - orphan chains;
  - jog density;
  - foreign-footprint threading (routes through other parts' pads);
  - traces not leaving from the pad centre;
  - track width below budget.
- **Track width is not enforced by KiCad.** It never enforces class widths. Validate track width against the current
  budget on every cleaning pass.
  - Example (DIN-8R): a 6-cap hold-up bank was fed by one 0.8 mm, 40 mm trace.
- **Never steer by open count alone.**

### 4.7 Vias
- If boards are ordered with epoxy-filled and copper-capped vias (IPC-4761 type VII), a true via-in-pad is legal: a
  via wholly inside its own-net pad, with margin.
  - Allowed only on pads of 0603 or larger parts. NEVER in 0402 pads.
  - Edge, partial or oversize vias on a pad are always defects.
- **Order note.** Fill and cap is usually a board-wide fab option. The order note must say "board-wide", including
  thermal-hole arrays. The order form governs, even if the board file's setup says no filling.

### 4.8 High-current paths
- **Dual outer paths.** Every high-current force connection (terminals, relay paths, shunts, line and neutral feeds)
  keeps an independently continuous, adequately sized path on BOTH outer layers, in the actual native-filled board.
  - Make the inventory of high-current connections explicit; do not silently exclude any.
  - A path through the opposite face, a narrow residual sliver, or a combined DC resistance that looks acceptable does
    not waive a missing face.
  - If a soldered wire is counted as part of a path, the BUILD instructions make that wire mandatory.
- **Validate after every refill.** Run the regression guard with negative fixtures that deliberately cut paths. A
  missing face is a RELEASE BLOCKER, even when its modelled heating is modest. Repair the geometry; never weaken the
  rule or the clearances.
- **Footprint-bound schemes.** Fault-path schemes bound to a footprint (via-in-pad arrays on a shunt land, an exit rule
  that keeps the shunt the first element to open) have their own apply and check scripts in the release script. A
  footprint, pitch, pad or net change is an ERROR until the scheme is redone.
- **Fault claims stay honest.** Analysis that shows an element is first to MELT does not show it opens before other
  joints reach their limits. State exactly what is proven.

### 4.9 Isolation, creepage, cross-layer
- **DRC is same-layer only.** DRC with custom rules covers same-layer clearance and creepage on every layer. It does
  NOT measure copper-to-copper distance between different layers. A separate cross-layer gate (plan view, every layer
  pair) is required.
- **Netlist isolation.** A netlist-level isolation check (union-find) proves the domains meet only through barrier
  parts.
- **Barrier bands** are keep-outs on ALL copper layers.
- **Each plane region** holds pads of one domain only.
- **Netless copper** (fiducials, mounting pads) must be mapped to an insulation domain by an explicit rule. Otherwise
  gates fail closed with "unmapped".

### 4.10 Silkscreen
- **Placement marks first.** Pin-1, polarity, cathode and outline-notch marks win every silk conflict: move the
  reference, label or logo instead.
- **Silk is a blocking release gate.** It runs in the release flow, never in the routing loop.
- **Dense-board policy (owner-approved).** References may be omitted from physical silk when they cannot be placed
  clearly:
  - record the exact omitted set;
  - keep every omitted reference in the interactive assembly map and the fab documentation, and prove it with a
    payload check;
  - this never permits omitting placement, pin-1 or polarity cues.
- **Accepted leftovers.** A few ambiguous designators with no legal spot can be accepted per board and refdes, with
  fixtures.

### 4.11 Decoupling, SI, current budget, fault qualification
- **Decoupling gate, both directions.** Cap side: each cap within N mm of its pin. IC side: every IC power pin has a
  bypass within the limit.
  - Side exceptions are bound per refdes, and a stale exception FAILs.
  - Read the design of record (section 4.1).
- **SI:**
  - **Formal SI gates** (per bus: timing, monotonicity, ringback, abs max, crosstalk, setup/hold) are slow. They run in
    the RELEASE flow only.
  - **During routing,** carry SI lessons through cheap layout checks (series-termination distance, diff pair,
    plane-slot, crystal, pad-axis) and through placement and router rules (terminations at the driver, impedance
    widths on outer layers only).
  - **Bus devices:** a new device on a bus re-opens that bus's timing gate, including write-direction setup/hold
    through repeaters.
  - **Stale models:** when a conductor's role changes (a reference becomes a limited supply), fix its SI model in the
    gate with a fixture.
- **Current budget:**
  - Every current-carrying net has a budget entry, with load and fault current at GUARANTEED limits (for example a
    regulator's maximum current limit, not its typical). A new net must not be left unbudgeted.
  - Required widths follow from IPC-2152 at the fab's tolerance floor: minimum width (for example −20 %) and minimum
    finished copper.
  - Fault-qualification holds close explicitly, each by an owner decision or a fix, until the hold list is empty.
  - If a regulator's current limit makes copper sizing impossible, a same-footprint part with a lower guaranteed limit
    is a valid fix. Check the start-up margin it costs, with guaranteed data.
- **Neck rule.** A short narrowing of a power track at a blocking object is allowed only with a bounded rise and
  fixtures.

### 4.12 Thermal and fans
- **Guaranteed data only.** Use guaranteed data for rating claims. A model estimate is labelled as an estimate. A
  thermal shortfall against a rating is the owner's decision (section 1.3), recorded with the derating alternatives.
- **No rating claim without proof.** No "guaranteed X A at Y °C" claim without a heat run, or a bound that meets
  section 2.8.
- **Fan rating credit:**
  - credit only at a guaranteed operating point: the maker's rated voltage and speed minus tolerance, verified live by
    tachometer for each unit;
  - quiet reduced speeds carry no credit;
  - firmware MUST derate to the no-fan thresholds on stall or low RPM; keep the no-fan case as the derate basis;
  - fix the mixing or bypass factor BEFORE seeing the result, and report the break-even value and the sensitivity;
  - check the fan's own ambient rating when it is stopped in hot interior air (it may not restart: the tach detects
    that).
- **Power audit.** When thermal margin is thin, recompute the logic envelope from per-part datasheet MAX currents.
  Then quantify the conversion-chain losses and each saving option, with guaranteed data.

### 4.13 Mechanical features on the board
- **Mounting holes** have keep-out rule areas on every layer (top, back, vias), checked by a gate. An exception is
  bound per item, side and hole (for example a flat fiducial with no body at a stated minimum distance).
- **Fiducials:** keep the global edge-distance rule. A per-dot override must be documented, and it is usually avoidable
  by searching harder.
- **Panel tabs:** parts near board edges limit where the panel's mouse-bite tabs can go. List the free tab x-ranges in
  the order note: tabs ≥ 3-5 mm from SMD parts, rails on the long edges, cut not snapped.

## 5. Release flow

### 5.1 Single final gate run
- **Workers check only what they change:** native clearance and connectivity of their objects, ERC, BOM and rotation
  checks, and model-specific SI.
- **Root runs full DRC and the complete gate suite ONCE,** on the merged candidate.
- **Full DRC runs only inside the release script.** The DRC tool refuses `--tier full` anywhere else. Working passes
  use the fast tier: cached, with constraints already proven by an equal clearance rule dropped.
- **Pre-release sweep:** a sweep of every gate except full DRC (`run_gates OUTDIR`) shows what blocks before the
  release run. Review gates (layout quality, placement) are non-blocking, but their findings must be unchanged or
  explained.

### 5.2 The release script
1. **Full DRC:** 0 physical errors, 0 unconnected, 0 schematic-parity errors.
2. **Every other gate:**
   - ERC;
   - silk;
   - 3D model coverage;
   - a frozen-fill check (a fresh native refill gives the same copper);
   - copper landing;
   - dual outer paths and entries;
   - footprint-bound schemes;
   - output-short and fault holds empty;
   - routing-branch baseline;
   - pickup and leakage models;
   - cross-layer isolation (on the design of record);
   - every SI gate;
   - prediction checks.
3. **Only after every gate passes:**
   - export Gerbers (X2), drill, job file, IPC netlist, STEP, renders and the position file;
   - write a manifest with the sha256 and byte count of every file, and a status line that says what is NOT signed off.
     Example (DIN-8R): `DRC_CHECKED_EXPORT_ENGINEERING_QA_NOT_SIGNED_OFF`.
4. **Exit codes:** exit non-zero on any failure, and delete the failed run's staging folder.

### 5.3 Typical release-run failures (fix the record, re-run; never weaken)
- **Schematic-parity drift in footprint fields.** Example: a `Note` text on the board differs from the regenerated
  schematic. Fix: copy the schematic values onto exactly those footprints (property lines only, no geometry). This
  makes a new board hash, so rebind every hash-bound package, then re-run.
- **Gate reading a stale design or the previous revision.** Fix the release path so it uses the design of record, add a
  fixture, and leave the threshold unchanged.
- **Gate with a missing default that fails closed.** Give it a sound default, for example the design file next to the
  board. A missing file must still fail closed. Add a test.
- **Stale test bounds after a budget change.** Update the fixture to read the computed value, and tell the workers not
  to edit it.
- **Expect several release runs.** Each run that fails on records only gets a QA_LOG row. The pass gets the release
  row.

### 5.4 Assembly exports
- Generate the assembler's BOM and CPL from the BOM JSON through the BOM writer, never by hand.
- Rotation QA gate (section 4.2 step 10) PASS, with the QA report regenerated on the release board. CONFIRM-status
  parts are checked in the assembler's preview.
- **Polarised parts:** a pin-1 rule per footprint pattern; update the pattern when the footprint name changes.
- **Alternates:** the recipe must say which column is the approved part (the design MPN in Comment, the assembler
  alternate as MPN).
- **Hash-bind the upload files** in the BOM JSON's release selection, and set the selection state to RELEASED.
- **Interactive assembly map (iBOM):**
  - generate it headless;
  - verify its payload: every placed refdes, every silk-omitted refdes covered, and negative fixtures rejected;
  - the payload proof is the binding check; a browser visual review is extra.

### 5.5 Order notes (generated into ORDERING.md and checked by the adversarial review)
- **Stackup:** layers, thickness, the fab's stackup code, outer and inner copper, Tg, mask and silk colours, surface
  finish, and whether impedance control is ordered.
- **Vias:** "Epoxy filled & capped, board-wide", including thermal-hole arrays.
- **Panel:** edge rails and mouse-bite tab ranges (section 4.13).
- **Assembly:** sides, attrition, consigned parts with the distributor and quantity, global-sourcing lines with quotes,
  MSL handling, and owner-only purchases flagged as OWNER ACTION.
- **Job-file fields:** if a field like revision or fill flag is wrong, but changing it would re-release the board, it
  may be ACCEPTED when the order form governs. Record the reason.

### 5.6 After release
- **Records:**
  - the working-board record (release-ready flag);
  - the checkpoint record;
  - the QA_LOG release row;
  - CLAUDE.md facts (release id, hashes, ordered list);
  - BUILD and README status lines;
  - the live block.
- **Adversarial review** (section 3.8). Apply the FIX items, and disposition the NOTEs.
- **Production designation record:** a canonical status JSON, plus a read-only verify script that checks every release
  hash.
- **A released or frozen board is frozen.** Copper, placement, footprints and fitted parts don't change. QA continues
  against it, but:
  - a model flag is not a defect;
  - prefer mitigations on the other board or in firmware;
  - routing proposals are future-revision work unless the owner reopens production.
  - A documentation fix may touch release records without touching fab files. Example (DIN-8R): a corrected 3D model
    propagated to the STEP, renders and coverage records; the board and Gerbers were unchanged and verify still
    passed.

## 6. Enclosure / mechanical

### 6.1 Order of work
- **Rebuild timing.** No enclosure rebuild or rebind until the boards are fully routed and their geometry has stopped
  changing. Queue enclosure-affecting changes (part moves, heights, removed parts, stale hashes) on a rebind list; do
  not build them.
- **Iterations:** iterate with the fast fit-only mode, in a sandbox.
- **ONE canonical build** (rebind + full build + prints + viewer) after the LAST enclosure revision. Interim builds
  waste hours and get superseded.
- **Sequential workers:** workers that edit the same generator run one after another. Each delivers diffs against the
  canonical hashes it started from.

### 6.2 Bound inputs and outputs
- **Hash-bound inputs.** The enclosure generator reads only hash-bound inputs:
  - board STEP, board facts and part heights;
  - the 3D-model asset map;
  - FFC or cable proofs;
  - fonts for legends.
  - It refuses an unbound or stale board.
- **One rebind command** re-runs the whole chain for one board: STEP export → inputs → QA → fixtures → full build →
  prints. Re-run it after any board or 3D-model change.
- **Prints only from the checked folder.** Printable files come ONLY from the `prints/` folder, which a collector
  script writes from a checked full build. The collector refuses:
  - an open (non-watertight) STL;
  - a multi-solid part;
  - a failed print-layer gate.
  - Never print from the working build folder.
- **Fit gates:**
  - interference threshold 0.01 mm³ (Example (DIN-8R): 0.5 mm³ hid real clashes);
  - one solid per printed part;
  - every STL watertight;
  - component envelopes current (re-export after any placement change, or the gate flags stale envelopes);
  - model coverage;
  - datasheet MAX heights;
  - lever, latch and connector-actuator sweeps;
  - wire-path and cable poses.
- **Every fixture is registered** in the test runner. A fixture that never runs proves nothing (Example (DIN-8R): one
  was found unregistered).

### 6.3 Printability
- **Print-layer gate.** Overhangs FAIL unless they sit inside declared, bed-reachable support-enforcer regions that the
  print procedure states: how to remove the support, how to finish the face, and the feeler check. Every other
  overhang still fails.
- **Bridges and thin walls.** State bridge-length and minimum-wall limits for the printer, for example walls of 2
  extrusion widths or more. Wall contracts below what FDM can print need a geometry change, such as a separate insert.
- **Slicer check.** Slicer-verify critical parts, such as latch roofs and inlay strokes: slice them and check the
  missing-stroke percentage.
- **Legends:**
  - a deboss filled flush by a second-filament inlay;
  - strokes at least 2 line widths;
  - a single-line, uniform-stroke font bound by hash;
  - legend text as large as the face allows; shorten wording before shrinking;
  - the inlay is never credited as insulation.
- **Material assumptions:** the body material is the ORDERED filament (frozen), and the material constants are stated
  against its datasheet.
  - Example (DIN-8R): the geometry used a lower E modulus than the datasheet, so strain gates were conservative but
    spring forces could be up to 1.7× higher.
- **Shrink:** measure it on a coupon and set the slicer compensation from the measurement.

### 6.4 First-article coupons
Before the full parts, print small coupons in a fixed order with the production settings. Each coupon has numeric pass
criteria, and its results go into QA_LOG. A typical sequence:
0. **Shrink bar:** x, y and z, measured 24 h or more after printing. Scale error ≤ 0.2 %.
1. **Appearance / material coupon:** light windows, legends and inlays.
2. **Board fit:** a bare PCB drops onto its pins and lifts out.
3. **Mounting:** DIN-rail latch on real rails from two makers.
4. **Wiring:** terminal and lever coupons with real parts: lever clicks, the cover descends with the levers open, and
   the wire-bend test.
5. **User interface:** button and display coupons with the real modules.
6. **Connectors:** connector collar and USB shell.
7. **Fasteners:** screw bosses in the real print orientation, 5 insert/remove cycles, strip torque ≥ 2× seating.
8. **Cables:** measure the delivered cable; insertion depth at both connectors (it sets the witness marks in BUILD).
9. **Snap features** that bend across print layers: 5 cycles, no whitening.

Then the full-print checks: flatness, joint feeler, rail pull and load tests, lift-off, hat or lid pull, and a hot
repeat within 10 min of the end of the heat run.

### 6.5 Class II / safety geometry
- **Distance to mains.** Accessible surfaces and metal must be at least the required distance from mains copper and
  bodies, by straight line: a lower bound for clearance and creepage. Example (DIN-8R): 6.5 mm.
- **Straight-wire probe.** Probe every opening with a straight wire at a fan of angles. A vent is measured from its
  outer mouth only if the test probes cannot enter it.
- **Insulating walls.** Solid insulating walls are ≥ 2 mm where they carry reinforced insulation, printed with 100 %
  infill and in the specified V-0 material. A legend floor is accessible surface and thins the wall.
- **Flex cables / FFC reach bound:** analyse every pose of the cable latched at both ends, every registration case,
  and the full cable-length range, minus the conductor half-width. Then:
  - longer-cable fallbacks have a hard cap from this bound;
  - a single disconnected end is a separate single-fault case (S1). If it is not proven contained, it is an owner
    residual decision (section 1.3), with procedural mitigations in BUILD: witness marks, actuator checks, never
    pulling a latched cable;
  - no opening over the cable's connector if the owner directs it;
  - an assembly order that cannot be met by a cable in stock becomes an owner order decision. Recommend the order
    early, so first assembly doesn't stall.
- **Per-unit insulation test** in BUILD: for example 500 V DC for 60 s, with a pass threshold. The optional hipot
  parameters are stated.

### 6.6 Thermal estimate honesty
- **What gets credited.** Credit only what is guaranteed (section 4.12): no stack flow while the fan runs, and the
  nominal maker P-Q curve scaled by the fan laws to the credited speed.
- **Openings.** Count every opening as a sharp-edged orifice from the generator geometry. Subtract recirculation leaks.
- **Thin passes.** A pass by a thin margin is a CONDITIONAL screen until the heat run. Log it under section 1.4 if it
  ships that way.
- **Fit-report items stay open.** Thermal fit-report items stay open and cite the decision entry. Gates are never
  relaxed to clear them.
- **Ambient vs cabinet.** Rated ambient is a stated condition. Cabinet ventilation can be an owner commitment outside
  agent scope.

### 6.7 Owner-fixed constraints
- **Record each one in HANDOFF "Owner rules / decisions to keep".** Examples:
  - connectors stay where they are and the screen aligns to them;
  - installation orientation;
  - board features are intentional;
  - approved courtyard-in-keep-out exceptions;
  - the screw supplier;
  - assembly order.
- **Re-read that list** before any enclosure brief.

## 7. Tooling gotchas (with the fix)

| Gotcha | Fix |
|---|---|
| Two Pythons: CPython for design, BOM and enclosure scripts; KiCad's bundled Python for anything importing `pcbnew` | Write which one each command uses. Run KiCad-Python scripts through a wrapper (`local_run.py`) that scopes all writable state to `.runtime/` (temp, KiCad config, matplotlib config, cache) and points library and 3D-model paths at assets staged in the repo. Never touch installed asset directories, and refuse scripts outside the workspace. |
| `pcbnew.SaveBoard` writes a DEFAULT `.kicad_pro` next to its output | Always restore the source `.kicad_pro` / `.kicad_dru` afterwards, and check the net classes survived. |
| `kicad-cli --save-board` or SWIG `Remove()` corrupts or drops items when scripted | Remove items through the project helper that deletes saved items safely, then refill natively. |
| DRC "0 unconnected" with a trace short of its pad (a pour bridged it); dead-tail checks count zones as hubs | Use the copper-landing gate (section 4.5); DRC is necessary, not sufficient. |
| KiCad never enforces netclass track widths | Run the TRACK-WIDTH check against the current budget. |
| DRC does not measure cross-layer distance | Use a separate cross-layer gate. |
| `kicad-cli` DRC is slow and shows "Not Responding" | Normal. Wait, or time out from its own launcher; never kill by name. Cache results, cap concurrency, use the fast tier in loops. |
| Router auto-flags and nondeterminism | Use deterministic mode (a fixed work schedule gives byte-identical plans). A variant killed at its timeout keeps its best legal checkpoint. |
| Geometry detectors with float rounding split T-junctions (false "dead branch") | Merge at a tolerance (for example 1e-5 mm) with a fixture, and re-baseline a reviewed branch list. |
| Windows console cp1252 crashes on °, Ω, µ | `sys.stdout.reconfigure(encoding="utf-8")`; always `open(..., encoding="utf-8")`. |
| CRLF files and LF diffs; `\r` left in path lists read from files | `patch --binary`; normalise, patch, restore. When reading lists of paths or names from a file, `.strip()` each line or use `splitlines()`, so a trailing `\r` doesn't break lookups. Line-ending format itself is not a quality target unless the owner says so. |
| InteractiveHtmlBom hangs on a hidden wx dialog when imported from a script | Set `INTERACTIVE_HTML_BOM_NO_DISPLAY=1` and `INTERACTIVE_HTML_BOM_CLI_MODE=1` BEFORE importing it. |
| `rm -rf $VAR/*` with an empty variable | Use `rm -rf "${VAR:?}/"*`. |
| STEP exports carry timestamps, so every regeneration changes the hash | Regenerate only the changed model (`--only`); bind the model-asset map, not incidental headers. |
| Library footprints with rotated variants (some oscillator footprints are rotated 90°); the assembler's library uses different origins per part number | Check pin 1 against the maker drawing; take rotation offsets from a per-part-number library check. |
| Supplier search quirks: fuzzy search wants one keyword; some makers are listed without hyphens | Use search only to find candidates, then look up the exact MPN; normalise hyphens; settle the maker with `--maker`. |
| Tests that use a real BOM MPN as a fixture break when the MPN leaves the BOM | Move them to an MPN with the same properties; pin export row order explicitly when shared lines regroup. |
| A tool run twice appends duplicate records | Make record writers idempotent (keyed entries); consolidate duplicates at once. |
| Shell `cd` doesn't persist between agent tool calls, and relative links resolve against the session root | Use absolute paths in commands; write links relative to the session root. |
| Long jobs in foreground tool calls time out | Run them in the background with completion notifications; give each a time budget; record PIDs. |
| The harness blocks a worker's write to its REPORT.md | The worker puts the full report in its hand-back message; the lead saves it (section 3.7). |
| Session or API usage limits (HTTP 429) stop workers mid-task | Persist the live block first; resume by message after the reset; re-launch workers that were cut off (section 2.6). |
| Something outside the agents deletes workspace dot-folders (preview `launch.json`, etc.) | Recreate only what is needed; note it in the running log; never rely on session scratch paths for anything persistent. |
| Viewer or preview servers pointing at a session scratchpad | Stage viewer files in the repo (`enclosure/build/viewer-site/`) and point the preview config there. |

**Migrating or consolidating a legacy folder into the repo:**
1. Inventory every reference to the folder (code, docs, records, runtime defaults).
2. Classify each item as migrate or delete.
3. Copy the items to migrate into the task folders and tool directories.
4. Make the code edits as exact-count literal replacements.
5. Regenerate the records that bind moved paths.
6. **Independence proof:** rename the old folder away, put a sentinel FILE at its path, and run the full test and gate
   sweep. No log may mention the old path.
7. Only then delete the folder, with the owner's explicit OK.
